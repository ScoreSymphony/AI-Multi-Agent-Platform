## Supported V1 baseline

The intended baseline is the self-hosted, local-first single-node product path documented by the
repository and exercised by the official first-run flow:

- browser-first onboarding plus CLI/operator alternatives;
- canonical Task -> Plan/Step -> Run -> Result/Artifact -> Verification lifecycle;
- versioned Control Plane with Web and CLI clients over the same canonical state;
- Agents/Agent Teams, model routing and capability/tool execution behind platform-owned contracts;
- Projects, Workspaces, Files and durable history/recovery;
- authentication, authorization, approvals, verification and secret-reference boundaries;
- local/reference operation without a mandatory paid AI/API service;
- official multi-agent first-run against an explicitly configured local/self-hosted text model.

The release does not make Hermes, LiteLLM, MCP, Forge or a paid model provider architectural
prerequisites for the baseline.

## Optional / advanced capabilities

These capabilities are outside the ordinary single-node baseline and must be claimed only where the
exact `1.0.0` candidate has matching conformance/compatibility evidence:

- distributed Node/Worker execution — **Beta**;
- Registry/Marketplace — **Beta**;
- Research / Decision / Application Distribution / Application Adapters — **Beta**;
- Backup/Restore — **Beta**;
- optional external adapters and integrations — maturity/support follows their individual
  compatibility records.

## Experimental capabilities

The following are not part of the Stable baseline compatibility promise and remain explicitly
Experimental unless the final candidate changes their classification with the required evidence:

- Control Plane high availability/failover profile;
- governed Learning;
- named enhanced repository-intelligence providers; the bundled ProjectAtlas candidate retains its
  explicitly pre-release compatibility bound unless separately revalidated for the final candidate;
- MCP Tasks interoperability profile.

## Public compatibility

Repository version `1.0.0` does not make every feature Stable. The authoritative per-surface
maturity remains `docs/FEATURE_CLASSIFICATION.md`.

Current Stable public foundations include:

- canonical Task/Run/Plan/Step lifecycle;
- Control Plane v1 shared protocol/foundation conventions;
- provider contracts v2.

Other named surfaces retain their documented Beta or Experimental maturity at publication unless
the final release candidate contains a separately reviewed classification change.

## Upgrade / recovery boundary

The final release evidence must record the supported transition from the maintained pre-release
state, including:

- exact migration/version-state expectations;
- required verified backup where the upgrade policy requires one;
- backup/restore evidence required by release policy;
- rollback/supersession behavior;
- preservation of historical canonical identities and provenance.

Historical baseline-adoption markers that intentionally reference `0.0.1` remain historical
evidence and are not mechanically rewritten to `1.0.0`.

For a tracked `0.0.1` data root, the first formal release is a release-only activation: the
canonical domain schema and migration revision remain unchanged, no synthetic `MigrationStep` is
invented, and `platform-upgrade ... apply --quiesced` activates the `1.0.0` version vector through
the normal durable maintenance path. An untracked data root must not be newly adopted by `1.0.0`.
The release procedure still requires a verified source-release backup before the executable is
replaced.
