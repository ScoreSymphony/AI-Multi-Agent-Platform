# Technical component curation review — 2026-09-09

This document records the second #638 curation evidence pass. It is review evidence, **not** a Registry provider input and not an adoption decision.

The loaded Marketplace remains governed by `catalog.json`. A row marked `candidate-ready` means source identity, license and current project status are sufficiently resolved for a later manual/untrusted catalog promotion. It does not mean installable, trusted, adopted or benchmark-approved.

## Decision vocabulary

- `candidate-ready`: eligible for a later `manual` / `untrusted` / `candidate` / `evaluation:required` catalog record.
- `reference`: useful to retain for comparison/history but should not be presented as an active candidate.
- `deferred`: identity is known, but current license/cost/dependency conditions do not fit a normal candidate card without an explicit governance decision.
- `needs-boundary-review`: source identity is known, but the actual distributable/model/subproject boundary is not yet sufficiently represented by the Registry metadata.
- `ambiguous`: the architecture name does not safely select one upstream.

## Promotion rules for this review

When the `candidate-ready` entries move into `catalog.json`:

1. keep `distribution_route: manual`;
2. keep `trust_status: untrusted`;
3. use `lifecycle:candidate` and `evaluation:required` unless an explicit reference/deferred decision above says otherwise;
4. do not invent upstream revisions;
5. preserve custom, modified, copyleft or non-commercial license terms explicitly;
6. keep provider, cost, network and resource facts `unknown` when not evidenced;
7. keep archived projects reference-only;
8. never substitute a fork/successor for an archived architecture item without documenting that governance decision.
