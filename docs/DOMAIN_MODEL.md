# Canonical Platform Domain Model

This document defines the platform-owned domain model for the AI Multi-Agent Platform. It is intentionally independent from Hermes, Forge, Temporal, LiteLLM, MCP implementations, model providers, storage engines and deployment products.

The executable reference definitions live in `src/ai_multi_agent_platform/domain/`. Serialized Task, Run and Event contracts live in `schemas/domain/` and are versioned independently from adapters.

## Design rules

1. Canonical entities are owned by the platform core.
2. External systems may map to these entities but may not redefine them.
3. Stable platform identifiers survive adapter replacement, retries, process restarts and node changes.
4. Runtime/provider-specific identifiers are stored only as external references.
5. Execution-relevant entities carry ownership, timestamps and correlation/provenance hooks.
6. Multi-user and organization ownership must be representable without changing identifier formats.
7. State transitions are explicit and deterministic; adapters cannot invent canonical lifecycle states.
8. Core domain code must import no Hermes-, Forge- or Temporal-specific types.

## Identifier model

Canonical identifiers are opaque strings with a type prefix and a UUID payload. Consumers must not derive semantics from the UUID payload.

Prefixes:

- `goal_<uuid>`
- `project_<uuid>`
- `task_<uuid>`
- `plan_<uuid>`
- `step_<uuid>`
- `run_<uuid>`
- `agent_<uuid>`
- `team_<uuid>`
- `artifact_<uuid>`
- `result_<uuid>`
- `event_<uuid>`
- `approval_<uuid>`
- `node_<uuid>`
- `worker_<uuid>`
- `worker_job_<uuid>`
- `tool_<uuid>`
- `cap_<uuid>`
- `model_assignment_<uuid>`

Canonical IDs are generated by the platform. Relationships use canonical IDs, never database-local integer identities. Task and Run IDs survive process restart and adapter replacement.

### External/backend identifiers

Backend-specific identifiers are represented only as `ExternalRef(system, kind, value)` entries. They are never canonical primary keys.

Examples:

- orchestrator workflow/run ID;
- executor job ID;
- provider request ID;
- storage-object identifier;
- remote scheduler handle.

A backend mapping may change or multiply without changing the canonical Task, Run or other entity identity.

## Common metadata

Persistent canonical entities support, where applicable:

- `id`;
- `schema_version`;
- `created_at` / `updated_at`;
- `owner_ref`;
- `project_id`;
- `provenance`;
- `external_refs`;
- implementation-neutral metadata.

Execution/event records additionally support:

- `correlation_id`: groups records belonging to one logical flow;
- `causation_id`: identifies the record/action that directly caused another record;
- `trace_id`: optional observability bridge and not a domain identity.

`owner_ref` is neutral and currently supports `user`, `organization`, `team`, and `service`. Authorization semantics remain a later concern; the ownership hook is reserved now so multi-user support does not require an identifier redesign.

`provenance` records a neutral source, optional actor reference and structured details. Provider-specific response objects do not belong in provenance.

## Canonical entities

### Goal

High-level desired outcome requested by a user, application or automation. A Goal may produce one or more Tasks and is not itself an execution attempt.

Core fields: ID, title, description, owner, project, timestamps, provenance and external references.

### Project / Workspace

Logical ownership and working boundary grouping Goals, Tasks, Agents, Artifacts and related configuration. It does not imply a filesystem layout or any provider-specific project concept.

Core fields: ID, name, owner, timestamps, provenance and external references.

### Task

Canonical unit of requested work. It captures platform intent and lifecycle independently from an orchestrator or executor.

A Task may reference one Goal and Project and may be associated with Plans, Runs, Artifacts, Results, Events and Approvals.

Task states:

```text
draft -> ready -> running -> succeeded
  |        |        |  |      
  |        |        |  +-> failed
  |        |        +----> waiting -> running
  |        |        +----> cancelled
  |        +-------------> cancelled
  +----------------------> cancelled

failed -> ready   (explicit retry/reset command only)
waiting -> failed | cancelled
```

`waiting` is the canonical paused state for approval, external dependency or another resumable condition. The reason for waiting belongs in associated state/event/approval data rather than a backend-specific Task status.

### Plan

Versioned decomposition of a Task into ordered and/or dependency-linked Steps. Once activated, a Plan revision is historical; replanning creates a new revision rather than overwriting execution history.

Core fields: ID, Task ID, revision, active flag, owner, project, timestamps and provenance.

### Step / Subtask

Executable or delegatable unit belonging to a Plan. A Subtask is represented as a Step relationship, not a second identity type. Nested work uses `parent_step_id`; dependency edges use canonical Step IDs.

Step states:

```text
pending -> ready -> running -> succeeded
   |        |        |  +----> failed
   |        |        +-------> waiting -> running
   |        |        +-------> cancelled
   |        +----------------> skipped | cancelled
   +-------------------------> skipped | cancelled

failed -> ready   (explicit retry/reset command only)
waiting -> failed | cancelled
```

### Run

One immutable execution-attempt identity for a Task or Step. A retry always creates a new Run ID and increments the attempt number; execution history is never rewritten into a new attempt.

Run states:

```text
queued -> starting -> running -> succeeded
  |          |          +-----> failed
  |          |          +-----> cancelled
  |          |          +-----> timed_out
  |          +----------------> failed | cancelled
  +---------------------------> cancelled
```

A Run's `subject_id` must be a canonical `task_...` ID when `subject_type=task` and a canonical `step_...` ID when `subject_type=step`. Backend workflow/job IDs belong in `external_refs`.

A Run may reference a canonical Worker ID when scheduled remotely, but the Worker is not part of the Run identity.

### Agent

Platform-owned reasoning/acting participant definition. It contains role/configuration references, required capabilities and optional Model Assignment reference without depending on an agent framework or model provider.

### Agent Team

Named grouping of canonical Agents plus coordination metadata. Team membership does not imply a fixed orchestration implementation.

### Artifact

Durable or version-addressable input/output/evidence object produced, consumed or attached during work. Payload storage is delegated to a provider boundary; canonical metadata and provenance remain platform-owned.

### Result

Semantic completion outcome for a Task or Run. A Result may reference zero or more Artifacts and is distinct from raw executor output.

### Event

Append-only canonical fact about a lifecycle transition or significant platform action. Events carry subject, correlation, causation, optional trace data, payload, provenance and external references. Events are facts and are never rewritten to represent a later outcome.

### Approval

Human or policy decision associated with a Task, Step, Run, Tool invocation or another governed action.

Approval states:

```text
pending -> approved | rejected | expired | cancelled
```

A Task or Step that cannot continue while an Approval is pending may move to `waiting`; an approval decision can causally produce the resume/failure/cancellation transition.

### Tool

Canonical description of an invokable platform tool independent of native, MCP, HTTP, plugin or another implementation transport.

### Capability

Implementation-neutral functional/property descriptor used to match requirements against Agents, Tools, Models, Nodes or Workers.

### Model Assignment

Versioned association between a subject and model requirements/provider selection. Provider-specific model handles are not canonical identity. Model assignments can be replaced without changing Task, Step or Agent identity.

### Node

Canonical compute device/runtime host participating in the platform. Hardware/vendor/deployment class belongs in metadata and capabilities, not identity.

### Worker

Execution-capable process/service registered on a Node. A Node may host multiple Workers. Workers advertise capabilities and availability independently from scheduler implementation.

### Worker Job

Canonical scheduling record connecting one Run to one Worker. It does **not** replace or duplicate Task/Run semantics; it represents only dispatch/execution placement.

Worker Job states:

```text
queued -> assigned -> starting -> running -> succeeded
  |         |           |          +-----> waiting -> running
  |         |           |          +-----> failed
  |         |           |          +-----> cancelled
  |         |           |          +-----> timed_out
  |         |           +----------------> failed | cancelled
  |         +----------------------------> cancelled
  +--------------------------------------> cancelled
```

This distinction allows the same canonical Run model to work with a local process, a remote VPS, a workstation, a cluster or a future scheduler.

## Relationship overview

```text
Project
  ├─ Goal
  │   └─ Task
  │       ├─ Plan (versioned)
  │       │   └─ Step ── parent_step_id / depends_on ──> Step
  │       ├─ Run
  │       ├─ Result
  │       ├─ Artifact
  │       ├─ Event
  │       └─ Approval
  ├─ Agent ── membership ──> Agent Team
  └─ shared Artifacts / configuration

Task/Step ──> Run ──> Result / Artifact / Event
Run ──> Worker Job ──> Worker ──> Node
Task/Step/Run/etc. ── may require ──> Approval
Agent/Task/Step/policy scope ── may use ──> Model Assignment
Worker/Node/Tool/Agent/Model ── advertises/requires ──> Capability
```

## Lifecycle invariants

- canonical IDs never change after creation;
- a retry creates a new Run ID;
- terminal Runs have no outgoing lifecycle transitions;
- Task/Step retry/reset transitions are explicit platform actions;
- Task terminal state is determined by platform lifecycle rules, not copied from backend status strings;
- `waiting` is resumable and distinct from failure;
- Events are append-only facts;
- active Plan replacement creates a new revision and preserves history;
- Artifacts retain provenance even if storage backends change;
- backend identifiers remain non-canonical external references;
- Worker Jobs represent placement and must reference an existing canonical Run and Worker.

Executable transition tables are defined in `src/ai_multi_agent_platform/domain/lifecycle.py`.

## Serialization and schema versioning

Externally visible canonical payloads carry `schema_version`. Initial contracts use `1.0`.

Rules:

- backward-compatible additive changes retain the current major version;
- removing required fields, changing required field types or changing field meaning requires a new major version;
- adapters/providers have their own versions and never replace canonical schema versions;
- readers reject unsupported major versions explicitly;
- migration logic lives at persistence/API boundaries and preserves canonical IDs and provenance;
- no Python/private class representation is the external contract.

Task, Run and Event JSON Schemas are the initial cross-boundary contracts. Additional entity schemas are added when those entities become externally exchanged rather than creating speculative provider-shaped contracts now.

## Adapter boundary

Adapters translate canonical contracts to/from backend concepts. Framework session objects, database row types, workflow handles and provider response classes must not become canonical domain types.

Example mapping:

```text
canonical task_id: task_<uuid>
  external_refs:
    orchestrator/run -> backend-run-42
    executor/job    -> backend-job-99
```

Changing the orchestrator or executor changes the mapping, not `task_id`.

## Required validation scenarios

The domain tests model all issue #4 scenarios:

1. one Task with one Run and one Artifact;
2. one Task retried through two Runs with distinct Run IDs;
3. one Plan with dependent Steps;
4. one Task paused in `waiting` for an Approval;
5. one Run dispatched to a remote Worker/Node through a Worker Job;
6. one canonical Task carrying external orchestrator-run and executor-job references without changing canonical identity.

Additional invariant tests reject malformed canonical UUID payloads, backend IDs used as canonical Run subjects and vendor/framework imports in the core domain layer.

## Deferred decisions

This domain model deliberately does not select persistence technology, event-store implementation, concrete orchestrator/executor APIs, model gateway, memory/vector backend, file/object storage product, final scheduler implementation, final authorization engine or UI representation. Later issues must map to this vocabulary instead of reshaping it implicitly.
