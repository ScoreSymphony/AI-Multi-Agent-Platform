# PostgreSQL coordination for multi-instance Control Plane HA

Issue #566 productionizes the active/passive semantics established by #89. This document covers the
first production-shaped boundary only: a real `CoordinationProvider` shared by independent processes
or hosts. It does **not** claim that the full #566 HA profile is complete. Shared canonical durable
state remains owned by prerequisite #956.

## Scope and architecture boundary

`PostgresCoordinationProvider` lives under the canonical `distributed` owner and implements the
existing `high_availability.contracts.CoordinationProvider` protocol. PostgreSQL does not become a
second leadership abstraction and is not canonical platform architecture.

The supported shape is:

```text
Control Plane A ----\
                    >---- PostgreSQL coordination row
Control Plane B ----/
```

The provider owns only lease/fencing coordination. Canonical Task, Run, Event, Agent, Workspace,
security, Automation and Worker state remains owned by the existing platform repositories/providers.
A deployment must not claim safe HA until #956 supplies or validates a shared/replicated durable-state
composition for every subsystem required by its failover claim.

The ordinary #39 single-node profile does not import or instantiate this adapter and requires neither
PostgreSQL nor Psycopg.

## Optional dependency

Install the explicit optional extra when using the adapter:

```bash
python -m pip install -e ".[ha-postgres]"
```

The extra pins `psycopg==3.3.5`. The platform imports Psycopg lazily only when a
`PostgresCoordinationProvider` is constructed, so normal platform imports stay PostgreSQL-independent.

A PostgreSQL 18.x service is the initial reviewed deployment target. The SQL intentionally uses only
ordinary transactions, row locks, `TIMESTAMPTZ`, `clock_timestamp()` and `ON CONFLICT`; broader server
version claims require retained compatibility evidence rather than assumption.

## Bootstrap and runtime identities

Create the adapter-owned table once before starting HA leadership:

```python
from ai_multi_agent_platform.distributed import PostgresCoordinationProvider

bootstrap = PostgresCoordinationProvider(
    "postgresql://<bootstrap-user>:<secret>@<private-db-endpoint>/<database>"
)
await bootstrap.initialize()
```

`initialize()` is adapter setup, not part of the canonical `CoordinationProvider` contract. This makes
it possible to use a schema/bootstrap database identity for DDL and a narrower runtime identity for
ordinary lease operations.

The runtime identity needs read/write access to the adapter table but does not need PostgreSQL to own
Task/Run lifecycle state merely because the same service is used for coordination.

Do not commit DSNs or credentials. Resolve them from the platform's normal secret/configuration
boundary. Non-loopback database traffic must use private/authenticated networking and TLS/service
identity according to the existing #36/#43 rules.

## Stored state

The adapter owns one row per configured `lease_name` in:

```text
ai_map_control_plane_coordination
```

Fields:

- `lease_name`: deployment-local coordination key;
- `epoch`: monotonically increasing fencing generation;
- `owner_instance_id`: current replaceable Control Plane process identity or `NULL`;
- `acquired_at`: backend timestamp for the current generation;
- `expires_at`: backend timestamp for current lease expiry.

No database hostname, provider/VPS identifier, password/token or backend-private row identifier becomes
canonical platform identity.

## Authority semantics

### Acquire

Acquisition runs in a database transaction and locks the lease row with `SELECT ... FOR UPDATE`.
Exactly one transaction can decide ownership at a time.

- a non-expired lease owned by another instance returns `LeadershipConflict`;
- reacquisition by the current non-expired owner returns the existing generation without extending it;
- an expired/leaderless row advances `epoch` exactly once and assigns the new owner;
- lease timestamps are generated by PostgreSQL, not by a Control Plane wall clock.

### Renew

Renewal locks the same row, validates owner + epoch + backend-observed expiry, and then extends
`expires_at` from `clock_timestamp()`. A stale/expired token raises `StaleFencingToken`.

### Release

Release locks and validates the row before clearing owner/timestamps. The epoch is retained so the next
acquisition receives a strictly newer generation.

### Fence validation

`assert_fence()` reads current backend state and rejects a token when instance, epoch or backend-owned
expiry no longer matches. This is the operation used by the existing #89 fail-closed authority checks
immediately before authority-bearing work.

### Inspect and backend outage

`inspect()` uses the backend clock when projecting expired leases. It never treats a local process
clock as proof of leadership.

Connection/transaction/backend failures are translated to `CoordinationUnavailable` with a generic
message. Raw driver errors and DSNs are not copied into canonical error text, avoiding accidental
credential leakage. The existing `ControlPlaneFailoverService` responds to this error by removing
write authority/fencing an active process.

## Async/cancellation behavior

Psycopg's synchronous DB operation is executed outside the event loop. Cancellation is deferred until
the in-flight transaction has reached its commit/rollback boundary, matching the platform's broader
rule that cancellation must not leave an unknown persistence transaction running in the background.
The caller still receives cancellation after the transaction boundary.

A cancelled successful acquisition can therefore leave a valid short-lived lease in PostgreSQL while
the caller unwinds. Retrying with the same `instance_id` returns that current generation; another
instance cannot take authority until release/expiry. This is fail-closed rather than split-brain.

## Readiness and deployment use

This adapter does not change #89 readiness semantics:

- standby can be healthy while not write-ready;
- `PROMOTING` is not write-ready;
- reconciliation must complete before the service becomes active;
- loss of coordination removes write authority;
- an old process with a stale epoch cannot regain authority through credentials alone.

A production-shaped deployment should route authority-bearing traffic only to the instance whose
existing HA status/readiness endpoint reports active + reconciled + coordination available.

## Test layers

Fast deterministic tests exercise the adapter contract without requiring PostgreSQL:

- simultaneous acquisition yields one leader;
- epochs remain monotonic across expiry/release;
- renew/release semantics;
- backend-owned expiry and stale fencing;
- backend outage mapping without DSN/secret leakage;
- cancellation waits for the transaction boundary.

An optional real integration test is gated by:

```text
AI_PLATFORM_TEST_HA_POSTGRES_DSN
```

When configured with the `ha-postgres` extra, the test bootstraps a unique lease key, spawns two
independent Python processes, proves exactly one wins acquisition, lets that process disappear without
release, promotes the other process after backend-observed expiry, and proves the old epoch is fenced.

This evidence proves real cross-process coordination only. It must not be reported as complete #566
multi-process/multi-host platform HA until #956 and the remaining #566 acceptance scenarios are green.

## Remaining #566 work

The following remain deliberately outside this first slice:

- shared/replicated canonical durable-state composition (#956);
- full two-Control-Plane composition and client routing;
- duplicate command replay against shared kernel persistence;
- authentication/session/revocation continuity against shared persistence;
- Worker re-registration and Automation single-fire over real process failover;
- multi-host/private-network acceptance evidence;
- optional #46 conformance result for the complete profile.
