# CLI compute administration

Issue: #214, Workstream C. Canonical compute contracts are owned by #14.

The `platform` CLI accesses Nodes, Workers and WorkerJobs only through the versioned Control Plane. It does not read the distributed registry, scheduler, Worker transports or runtime persistence directly.

```text
platform node / worker / worker-job
              |
              v
       /api/v1 Control Plane
              |
              v
    #14 distributed services
```

## Inspection

```bash
platform node list
platform node show node_...
platform worker list
platform worker show worker_...
platform worker-job list
platform worker-job show worker_job_...
```

List commands support the normal CLI page options: `--limit`, `--cursor`, `--sort`, `--direction`, `--q`, repeatable `--filter FIELD=VALUE`, and `--fields`.

The Node projection exposes canonical health/heartbeat state, CPU/RAM/storage availability, accelerator metadata when present, runtime/model/capability availability, trust, locality, draining and maintenance state. The Worker projection exposes health/heartbeat state, executor/runtime/model/capability availability, concurrency/current active jobs and draining state. WorkerJob inspection exposes canonical placement, requirements, execution state, result/artifact/evidence metadata and reconciliation errors. Secret references are not projected.

Scheduler candidate/rejection details are not given a CLI-only representation. They remain available only where the owning canonical Control Plane/telemetry surface exposes them; the CLI does not query the scheduler directly.

## Administration

The #14 Control Plane exposes these commands:

```bash
platform --yes node drain node_...
platform --yes node undrain node_...
platform --yes node maintenance-enable node_...
platform --yes node maintenance-disable node_...
platform --yes worker drain worker_...
platform --yes worker undrain worker_...
```

Every mutation:

- requires the normal CLI confirmation flow (`--yes` for non-interactive use);
- is sent to `/api/v1/commands/node.*` or `/api/v1/commands/worker.*`;
- carries an `Idempotency-Key` (generated by the CLI or supplied with `--idempotency-key`);
- remains subject to the canonical #15 Control Plane authorization boundary;
- never mutates the Worker registry or scheduler from CLI code.

## Doctor integration

`platform doctor` treats the distributed compute extension as optional for installations that do not register `nodes` and `workers`. If both collections are absent, the existing single-node/basic Control Plane diagnosis remains healthy.

Once the compute surface is registered, `doctor` reports Node and Worker health individually. Offline, degraded, draining or maintenance Nodes and degraded, unhealthy, offline or draining Workers make the diagnostic result `degraded` (exit code `1`) without redefining Control Plane reachability/readiness failures, which remain blocking.

This keeps deployment-neutral health semantics: a laptop, server, VPS or other host is evaluated only through canonical Node/Worker state, never through provider- or hostname-specific logic.
